# Online TPC-C evaluation harness

This one-off harness uses the Go SQLite SDK through the local `bridge.go` HTTP adapter and the five transactions from the pinned py-tpcc implementation. It is not an official TPC-certified benchmark.

Runtime inputs belong to this worktree's ignored `.work/` directory. `.work/private/` holds the dedicated test account cookies and instance endpoint tokens with restricted file permissions. Never commit these files. The sibling specifications worktree receives dated, redacted experiment evidence; SQL text and credentials are excluded from request logs.

Each instance contains one full warehouse, generated with seed 20261010. Runtime transactions use seed `20261010 + instance_number` and py-tpcc's 45/43/4/4/4 mix. The driver uses real BEGIN/COMMIT/ROLLBACK boundaries. Fixture import temporarily disables foreign-key checks in the import session; workload sessions retain the product default.

`workload.py run NUMBER PHASE SECONDS QPS` runs a bounded session. The standard capacity phase is 420 seconds at a target of 12 SQL requests per second, with 120 seconds of warmup and a 300-second measurement window. Business SQL QPS excludes transaction-control statements. Cold connection latency is the first request only and is recorded separately. After the first request completes, the guard waits for a full 30-second window, then computes nearest-rank p90 from requests in the preceding 30 seconds. SQL latency is observation-only under the updated user protocol; complete windows retain p90, p99, maximum, and observed QPS. SDK request timeout is 30 seconds. On a transaction error, the failed or uncertain result is recorded, the session is closed, and a fresh session generates a new transaction; the failed SQL/transaction is not replayed.

`observe.py` checks all seven online nodes every five seconds. CPU checks both one-minute idle-counter rate and irate; the non-idle result includes I/O wait. Memory uses `1 - MemAvailable / MemTotal`. CPU or memory >=95%, missing monitoring, or stale/nonfinite monitoring writes `.work/STOP`. The separate watermark observer records85% crossings. Every workload checks this flag before issuing SQL. Observer queries, original responses, source labels, and sample timestamps are preserved. The published Prometheus query endpoint does not expose its replica identity.

`workload.py load NUMBER [COMMITTED_BATCHES_TO_SKIP] [FIXTURE_CHUNKS_PER_BATCH]` imports the fixture. Each source chunk has at most 100 rows. Initial imports use five chunks per batch; instances010–129 use50 and instances130 onward use200, locally verified against the complete fixture and the8MiB product request limit. The200-chunk online pilot acknowledged all598056 inserted rows in260 SQL requests without errors. Resume only from the exact number of acknowledged COMMITs and with the original batch size. Do not replay a batch with an uncertain commit result.

`density-stage.py PHASE NEW_NUMBERS ACTIVE_NUMBERS` creates the requested dedicated instances, imports at most sixteen simultaneously, then runs all active instances for 420 seconds. It records actual placement every 30 seconds. Eight instances are allocated per dedicated test account to stay within the existing per-tenant quotas. It does not change global quota, scheduling, resource limits, or production binaries. Worker errors are recorded and do not set the resource stop flag. The initial `after-baseline` option is specific to the first staged run.

`analyze-phase.py NUMBER:PHASE ...` and `analyze-resources.py START END PHASE` preserve derived measurement summaries. `reconcile-stage.py PHASE NUMBERS` compares producer counter maxima across stage boundaries; fixture-to-workload transitions within a scrape interval require separate accounting and are not evidence of dropped telemetry.

The local observers and bridge are long-running processes and must be terminated after recovery observation. After evaluation, the user requested deletion of all recorded test instances. `cleanup-group.py GROUP` uses the recorded account/instance ownership and saves each asynchronous deletion result. Final deletion and inventory verification are recorded separately from benchmark measurements. Account ownership remains in the private archive and redacted evidence manifest.

From the 128-instance ramp, `.work/RETAIN-SESSIONS` retains successful fixture/workload connections between stages. The next successful connection replaces and closes the previous one. Remote close errors are recorded separately because the SDK still releases its local transport; they do not fail the new SQL. This separates steady density measurement from the already-observed synchronized idle-stop overload. `retained-session-guard.py` closes retained sessions on resource STOP. Final cleanup must also close every retained session. Retained idle connections issue no SQL and are distinguished from active TPC-C workload instances.

`prepare-instances.py NUMBERS` prepares future idle instance definitions using three independent browser sessions per account, with sequential mutations in each session. Login setup is sequential and respects the deployed limit of three logins per minute per account. Sharing a rotating CSRF session across parallel mutations previously produced rejected requests; that evidence is retained. Preparation of future definitions may overlap the current stage and is explicitly timestamped.

## Simple CRUD retest

`crud-sql.py` implements the corrected read50% / write50% workload. Each shuffled six-statement cycle has three primary-key SELECTs, one INSERT, one primary-key UPDATE, and one primary-key DELETE. At12 total SQL requests/s, the targets are6 SELECTs/s and2/s of each write type. Statements run serially in autocommit mode. The dedicated table has1000 persistent seed rows and one rotating inserted row; successful cycles preserve1001 rows. Every mutation targets a single row.

`crud-density.py PHASE` prepares and reuses test instances, opens a fresh measurement session after preparation, and increases per-node density with smaller steps near400. Cold preparation, full30-second latency windows, SQL operation kinds and affected-row counts remain separately recorded. The measured rate can fall below the target when response time exceeds the rate interval. `analyze-crud-mix.py PHASE` verifies actual mix and affected rows in completed windows.

Set `TPCC_EVIDENCE_DIR` to a new dated experiment directory for a separate round. The2026-10-10 retest writes to the original assessment’s `evidence/crud-r1/`; its first phase was aborted for old tenant quota rejections, and `crud-density-r2` completed lower-density windows before a stale preparation session interrupted its ramp; `crud-density-r3` uses fresh measurement sessions and continues from64/node. The prior SELECT+INSERT artifacts remain in the original evidence directory. Never start another coordinator for a phase that is already running or reuse a table after an outcome-unknown mutation.
